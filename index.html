    How Java runs

    Java is compiled, but not to your machine. The javac compiler turns your source code into bytecode: instructions for an imaginary computer called the Java Virtual Machine. Any device with a JVM can run that bytecode unchanged. That is the whole idea behind “write once, run anywhere”.

    Hello.javaSource code you write
    →
    javacCompiler checks types and emits bytecode
    →
    Hello.classPlatform-neutral bytecode
    →
    JVMLoads, verifies, interprets, then JIT-compiles hot code

    The JVM starts by interpreting bytecode one instruction at a time. While it runs, it counts which methods are called most and compiles those to native machine code with its just-in-time (JIT) compiler. That is why a Java service starts out slower and speeds up gradually over its first few minutes of work, a period called warm-up: it is learning where your program spends its time, then compiling those parts.

    Three names you will hear

    JVM
    The virtual machine that executes bytecode, manages memory and runs the garbage collector.
    JRE
    The JVM plus the standard library: enough to run Java programs, but not to compile them. Until Java 8 it was a separate download for end users. Since Java 11 there's no separate JRE; to run an app, you either install a JDK, or use the JDK's jlink tool to build a small custom runtime containing only the parts your app needs. The Modules lesson shows how.
    JDK
    Everything a developer needs: the runtime plus tools like javac, java, jshell, jar and javadoc. Install this.

    Java 25 finalised compact source files and instance main methods. A file can now contain just methods and fields.     Variables and primitive types

    A variable is a named slot that holds a value of one fixed type. Java is statically typed: the compiler knows every variable's type and refuses to put the wrong kind of value in it, which catches a whole class of bugs before your program ever runs.

    Java has eight primitive types, stored directly as raw bits. Everything else is a reference to an object.

    Converting between types

    Watch out. double cannot represent most decimal fractions exactly: 0.1 + 0.2 is 0.30000000000000004. Never use it for money. Use java.math.BigDecimal, or store amounts as a long count of cents.

    Operators

    Operators combine values into new values. Most behave as you would expect from school maths, with two surprises worth learning now: integer division, and the difference between x++ and ++x.

    Logical and bitwise

    && stops as soon as the left side is false, and || stops as soon as it is true. That is why s != null && s.isEmpty() is safe. The bitwise operators & | ^ ~ << >> >>> work on the individual bits of integers; you will meet them in flags, hashing and low-level code.

    When in doubt about precedence, add parentheses. (a + b) * c is clearer than memorising the table, and costs nothing at runtime.

    + is evaluated left to right. 1 + 2 is the number 3. Then 3 + "3" becomes the string "33", and from there every + is string concatenation: "334", then "3345".

    Numbers, Math and exact decimals

    Java gives you three toolkits for numbers: the Math class for calculations, the wrapper classes like Integer for parsing and converting, and BigDecimal and BigInteger for when double and long aren't exact or big enough.

    Formatting numbers

    Exact decimals with BigDecimal

    A double stores binary fractions, so most decimal amounts are approximations. BigDecimal stores decimal digits exactly, which is why it's the standard for money.

    Two traps. new BigDecimal(0.1) copies the double's inexact value and gives 0.1000000000000000055511…; use new BigDecimal("0.1"). And equals treats 2.0 and 2.00 as different because their scales differ; use compareTo to compare amounts.

    Check yourself

    What does Math.round(-2.5) return?

    Math.round adds 0.5 and takes the floor: −2.5 + 0.5 = −2.0, floor −2. So halves round toward positive infinity, not away from zero. It returns a long for a double argument, so the result is −2, not −2.0.

    Strings and text

    A String is an object holding a sequence of characters. Strings are immutable: every method that looks like it changes one actually returns a new string. That makes them safe to share between threads and use as map keys.

    Comparing strings

    == compares references: are these the same object in memory? equals compares contents. For strings you almost always want equals, or equalsIgnoreCase.

    Text blocks Java 15

    Triple quotes create a multi-line string. Indentation common to every line is removed, so you can indent the block with your code.

    Building strings efficiently

    Concatenating in a loop creates a new string every time. A StringBuilder is a mutable buffer designed for this.

    A feature that didn't ship. You may read about “string templates” (STR."Hello \{name}"). They were previewed in Java 21 and 22, then withdrawn in Java 23 for a redesign. Use formatted or concatenation today.

    What does this print?

    String literals are shared from a pool, but new String(...) always creates a separate object. Same contents, different references.

    Making decisions and repeating

    Programs become interesting when they choose between paths and repeat work. Java's tools for this are if, switch and four kinds of loop.

    Switch expressions Java 14

    The modern switch uses arrows, produces a value, and never falls through to the next case. Use yield to return a value from a block.

    Watch out. The older colon form, case 1:, falls through into the next case unless you write break. It still compiles, and forgetting break is a classic bug. Prefer arrows in new code.

    Arrays

    An array is a fixed-length row of values of one type, numbered from zero. Arrays are the lowest-level collection in Java; most code uses List instead, but arrays are everywhere underneath.

    New arrays are filled with default values: 0 for numbers, false for booleans, '\u0000' for chars and null for objects. Reading or writing past the end throws ArrayIndexOutOfBoundsException.

    In practice. An array cannot grow. If you don't know the size up front, use ArrayList from the Collections lesson. Printing an array directly shows something like [I@1b6d3586; use Arrays.toString.

    Methods

    A method is a named, reusable block of code. It takes parameters, may return a value, and is the main unit you will use to break a problem into pieces.

    Java always passes by value

    Java copies every argument. For a primitive, the copy is the number itself. For an object, the copy is the reference: both the caller and the method point at the same object. So a method can change the object's contents, but reassigning its parameter has no effect outside.

    Recursion

    A recursive method solves a problem by calling itself on a smaller version of the same problem. It needs a base case that stops, and a recursive case that moves toward it.

    factorial(3)waits for factorial(2)
    →
    factorial(2)waits for factorial(1)
    →
    factorial(1)base case: returns 1
    →
    Unwinding2 × 1 = 2, then 3 × 2 = 6

    Each call gets its own frame on the thread's stack, holding its own n. Frames pile up until the base case returns, then finish in reverse order.

    Divide and conquer

    Remember results you've already computed

    Naive Fibonacci calls itself on the same values again and again, an exponential amount of work. Storing each result, called memoization, makes it linear.

    Watch out. Don't write this as memo.computeIfAbsent(n, k -> fib(k - 1) + fib(k - 2)). Changing a HashMap from inside its own computeIfAbsent throws ConcurrentModificationException. And very deep recursion, typically thousands of levels, exhausts the stack with StackOverflowError; Java doesn't optimise tail calls, so rewrite deep recursion as a loop.

    Check yourself

    What happens when you call countdown(3)?

    There's no base case, so the calls never stop until the thread's stack is full. Add if (n < 1) return; at the top.

    Reading errors and debugging

    Java programs fail in three ways: the compiler rejects the code, the program crashes with an exception, or it runs but gives the wrong answer. Each has its own way of finding the cause.

    Compile errors

    The compiler gives the file, the line, a caret under the problem, and what it expected. Fix the first error first; later ones are often caused by it.

    Runtime exceptions and stack traces

    The first line names the exception and what went wrong. Below it is the stack of method calls, most recent first: the crash happened at line 12 inside total, which was called from checkout, which was called from main. If there's a “Caused by:” section further down, the root cause is usually the last one.

    ExceptionUsually means
    NullPointerExceptionCalling a method on a variable that holds null. The message names exactly what was null.
    ArrayIndexOutOfBoundsExceptionAn index of −1 or ≥ length; often a loop with <= instead of <
    NumberFormatExceptionInteger.parseInt on text that isn't a number
    ClassCastExceptionCasting an object to a type it isn't
    ConcurrentModificationExceptionChanging a collection while looping over it

    Using a debugger

    Every Java IDE, such as IntelliJ IDEA, VS Code with the Java extensions, or Eclipse, has a debugger. Click in the margin to set a breakpoint, run in debug mode, and execution pauses on that line. Then step over runs the line, step into enters the method it calls, and the variables panel shows every value. It's far faster than adding print statements.

    For logic errors. When the code runs but the answer is wrong, write down what you expect at each step, then use the debugger to find the first place reality differs. Explaining the code line by line to someone, even a rubber duck, finds a surprising number of bugs.

    Classes and objects

    A class is a blueprint: it describes what data something holds (fields) and what it can do (methods). An object is one concrete thing built from that blueprint with new.

    When you write new BankAccount(...), the JVM allocates the object on the heap and runs the constructor. The variable acc holds a reference to it. When nothing references the object any more, the garbage collector reclaims its memory. You never free memory yourself.

    If you write no constructor, Java provides a no-argument one. As soon as you write any constructor, that default disappears.

    Static versus instance. Instance members belong to each object. Static members belong to the class itself. A static method cannot use this, because there is no object.

    Encapsulation, packages and access

    Encapsulation means an object guards its own data. Fields are private, and the only way to change them is through methods that keep the object valid. Callers can't put it into a broken state.

    Packages

    A package groups related classes and gives them a namespace. By convention it is your domain reversed. The folder structure mirrors the package name: com/example/bank/Account.java.

    In practice. Start every field as private and every class as package-private. Widen access only when something outside genuinely needs it. Avoid auto-generating a setter for every field; add methods that express what callers actually want to do, like deposit rather than setBalance.

    Inheritance and the Object class

    A class can extend one other class, inheriting its fields and methods and overriding the ones it wants to change. Java allows only single inheritance of classes.

    @Override asks the compiler to check that you really are overriding a parent method. Without it, a typo like Sound() silently creates a new method. A final method can't be overridden, and a final class, like String, can't be extended.

    Every class extends Object

    If you don't write extends, your class extends java.lang.Object. Three of its methods you will override often: toString for readable output, and equals with hashCode for value comparison.

    Watch out. If you override equals, you must override hashCode so that equal objects have equal hash codes. Otherwise HashMap and HashSet will lose your objects. Records, two lessons from now, generate both for you.

    Polymorphism and abstract classes

    Polymorphism means one piece of code can work with many types. You write code against a general type, and at runtime each object runs its own version of the method. This is called dynamic dispatch.

    An abstract class can't be instantiated. It exists to share code and define methods its subclasses must fill in. The loop above never checks which shape it has; it just calls summary(), and the right area() runs.

    Interfaces

    An interface is a contract: a list of methods a type promises to provide. A class can extend one class but implement any number of interfaces, which makes interfaces Java's main tool for describing capabilities.

    Payable has exactly one abstract method, so it is a functional interface and can be implemented by a lambda, as free() does. You will use this constantly from the Lambdas lesson onward.

    When two defaults collide

    Interface or abstract class? Use an interface to describe what something can do, especially when unrelated classes share the ability. Use an abstract class when subclasses share state (fields) and a common constructor. Most designs need interfaces far more often.

    Records

    A record is a class whose job is to carry data. You declare the components once, and Java generates the constructor, accessors, equals, hashCode and toString. The fields are private and final, so records are immutable by default.

    Records can implement interfaces, have static fields and methods, and declare extra constructors. They can't extend another class (they implicitly extend java.lang.Record) and can't declare extra instance fields.

    Shallow immutability. A record holding a List can't swap the list for another, but the list itself might still be changed by someone else. Copy it in the compact constructor: items = List.copyOf(items);

    Enums

    An enum is a type with a fixed set of named instances. In Java, enums are full classes: each constant can carry fields and the enum can have constructors and methods.

    In practice. Reach for an enum whenever a value can only be one of a known list: statuses, directions, roles. Don't persist ordinal() to a database; reordering the constants would silently change every stored value. Store name() instead.

    Sealed classes and interfaces

    Normally anyone can implement your interface or extend your class. A sealed type lists exactly which types may extend it. That turns an open hierarchy into a closed, known set, and the compiler can then check that you handled every case.

    Each permitted subtype must declare how it continues the hierarchy: final (no further subclasses), sealed (its own permitted list) or non-sealed (open again). If you later add a Bus to the permits list, every switch that doesn't handle it stops compiling. That is the point: the compiler finds every place you need to update.

    Nested, inner and anonymous classes

    Classes can be declared inside other classes. Which kind you choose decides whether the inner class is tied to an instance of the outer one.

    Prefer static nested classes. An inner class silently holds a reference to its outer object. If the inner object lives longer, for example as a listener or a cached task, it keeps the outer object alive too. That is a common source of memory leaks.

    Flexible constructor bodies

    For thirty years, a call to super(...) or this(...) had to be the very first statement in a constructor. That meant you couldn't validate arguments before the parent did work with them. Java 25 lifts the rule.

    The statements before super(...) are called the prologue. In it you can compute values, check arguments and assign this class's own fields. You can't read fields or call instance methods, because the object isn't fully constructed yet.

    Assigning fields early also fixes a long-standing trap: if the parent constructor calls an overridden method, that method now sees your fields already set instead of their default null or 0.

    Exceptions

    An exception is an object that signals something went wrong. Throwing one stops normal execution and unwinds the call stack until some code catches it. If nothing does, the thread dies and prints a stack trace.

    Try-with-resources Java 7

    Anything that implements AutoCloseable, like files, sockets and database connections, is closed automatically when the block ends, even if an exception is thrown.

    Generics

    Generics let a class or method work with any type while keeping type safety. A List<String> only accepts strings, and you never need to cast what comes out.

    Wildcards

    A List<Integer> is not a List<Number>, even though an Integer is a Number. Wildcards express flexible relationships. The rule of thumb is PECS: producer extends, consumer super.

    Erasure and boxing

    Generic types exist only at compile time; the JVM sees plain Object. That is called type erasure, and it's why you can't write new T() or List<int>. Primitives are automatically boxed into wrapper objects like Integer, Long and Double when they go into a collection.

    Stream gatherers

    For ten years, the set of intermediate stream operations was fixed. If you needed sliding windows or a running total, you dropped back to a loop. Gatherers, final in Java 24, let anyone add new intermediate operations through stream.gather(...).

    mapConcurrent is particularly useful: it runs a blocking function on virtual threads with a concurrency limit, and keeps results in the original order.

    Going further. You can write your own by implementing Gatherer or using Gatherer.of(...), which takes an integrator function and optional initialiser and finisher. Collectors are to collect what gatherers are to gather.

    Optional

    Optional<T> is a box that either holds a value or is empty. Returning one says clearly “there might be no result”, so callers can't forget to handle that case the way they forget to check for null.

    Rules that keep Optional useful. Use it as a return type. Don't use it for fields, method parameters or collections; an empty list already means “nothing”. Never call get() without checking; prefer orElse, orElseThrow or map.

    Files and I/O

    The java.nio.file API, built around Path and the Files helper class, covers almost everything you need for files and folders, usually in a single line.

    For streaming large files line by line, use Files.newBufferedReader and newBufferedWriter. Since Java 18, the default character set everywhere is UTF-8, so files read the same way on every operating system.

    Watch out. Files.lines and Files.walk keep the file or directory open until the stream is closed. Always use them inside try-with-resources. And avoid Java's built-in object serialization for new code; it has a long history of security problems. Use JSON or another explicit format.

    Regular expressions

    A regular expression is a compact language for text patterns, like “three digits, a dash, four digits”. Java's java.util.regex package uses them to search, validate, extract and replace text.

    find() looks for the next match anywhere; matches() requires the entire input to match, which is what you want for validation. Pattern.compile is relatively expensive, so store compiled patterns in static final fields rather than calling String.matches in a hot loop.

    Don't overuse them. For simple checks, string methods are clearer: startsWith, contains, isBlank. Never parse HTML or JSON with regex; use a parser. And for user-supplied patterns, beware of patterns with nested quantifiers like (a+)+, which can take exponential time.

    Databases with JDBC

    JDBC is Java's standard API for talking to relational databases. The same code works with PostgreSQL, MySQL, SQLite, Oracle or H2; only the connection URL and the driver dependency change.

    Connections, statements and result sets all hold database resources, so each goes in try-with-resources. Placeholders are numbered from 1, not 0.

    Transactions

    SQL injection. Never build SQL by concatenating user input: "SELECT * FROM users WHERE name = '" + name + "'" lets an attacker type ' OR '1'='1 and read every row. A PreparedStatement with ? placeholders sends values separately, so the database treats them strictly as data.

    In real applications, a connection pool such as HikariCP reuses connections, because opening one is slow. Most teams also use a higher-level tool on top of JDBC: JPA with Hibernate maps tables to classes, Spring Data generates queries from method names, and jOOQ builds type-safe SQL in Java.

    Check yourself

    Which line is safe when name comes from a web form?

    Only the prepared statement keeps the value out of the SQL text. Concatenation and formatted both paste the user's text straight into the query.

    Pattern matching

    Pattern matching lets you test what shape a value has and pull it apart in one step. It arrived in stages: instanceof patterns in Java 16, then patterns in switch in Java 21.

    Patterns in switch

    Cases are checked top to bottom, so put specific patterns before general ones; the compiler rejects a case that can never match. A when clause adds a condition. Without case null, a null value still throws NullPointerException, as switch always has.

    When the selector is a sealed type, the switch must cover every permitted subtype, and then needs no default. You saw this in the Sealed lesson; it is what makes the next two lessons work.

    Still in preview. Primitive types in patterns extends all of this to int, double and the other primitives, for example case int i when i > 100 on an int selector, and checks whether a conversion would lose information. It has been in preview since Java 23. Try it with --enable-preview.

    Record patterns and unnamed variables

    A record pattern takes a record apart into its components right inside an instanceof or case. Patterns can nest, so you can match deep structures in one line.

    Unnamed variables and patterns Java 22

    The underscore _ means “I need something here, but I won't use it”. It makes intent explicit and silences unused-variable warnings.

    Data-oriented programming

    Records, sealed types and pattern matching were designed to work together. Combined, they give Java a style called data-oriented programming: model your data as plain, immutable records in a closed hierarchy, and write operations as switches over that data.

    Here is a complete little expression language: a data model, an evaluator, a printer and a simplifier.

    Adding a new operation, like show, means writing one new method; no existing class changes. Adding a new kind of expression, like Div, means adding a record, and the compiler then lists every non-exhaustive switch you need to update.

    Objects or data? Classic object-oriented design puts behaviour inside each class and is best when the set of operations is fixed but new types appear often, like plugins. Data-oriented design is best when the set of types is fixed but operations keep growing, like parsers, API messages and domain events. Modern Java lets you use both.

    Modules and module imports

    A module is a named group of packages with an explicit list of what it needs and what it shares. Introduced in Java 9, modules give strong encapsulation: a package that isn't exported is invisible outside, even if its classes are public.

    Custom runtimes with jlink

    The JDK itself is split into about seventy modules, such as java.base for the core classes, java.sql for databases, java.net.http for the HTTP client and java.desktop for windows and graphics. A typical web service never uses java.desktop, yet a full JDK ships it anyway.

    jlink builds a trimmed runtime: a ready-to-run Java folder, with its own bin/java, containing only the modules your app needs. Your app doesn't have to use modules itself; a normal JAR works.

    Threads and shared state

    A thread is an independent path of execution. Several threads let a program do many things at once, but the moment they share data that changes, you need to coordinate them.

    Race conditions

    Both threads read the same old value, add one, and write back, so increments get lost. Two fixes:

    Visibility

    Without synchronisation, one thread may never see another thread's writes; each CPU core can keep values in its own cache. The Java Memory Model defines “happens-before” rules: releasing a lock, writing a volatile field or starting a thread all publish earlier writes to the threads that follow. Mark a simple flag volatile when one thread writes it and others read it.

    Deadlock. If thread A holds lock 1 and waits for lock 2, while thread B holds lock 2 and waits for lock 1, both wait forever. Always acquire multiple locks in the same order.

    The concurrency toolkit

    You rarely create raw threads in real code. The java.util.concurrent package gives you thread pools, futures, locks, atomic variables and thread-safe collections, all written by experts and battle-tested for two decades.

    CompletableFuture Java 8

    A CompletableFuture describes a chain of asynchronous steps that run when their inputs are ready, without blocking a thread while waiting.

    Which to use? For CPU-heavy work, a fixed pool sized to your core count. For work that mostly waits on network or disk, virtual threads, next lesson, usually beat both thread pools and long future chains in clarity.

    Virtual threads

    A normal Java thread maps to an operating-system thread, which costs about a megabyte of stack and is slow to create. A server can afford a few thousand. Virtual threads, final in Java 21, are managed by the JVM instead: you can run millions, and blocking one is nearly free.

    When a virtual thread blocks on I/O, the JVM unmounts it from its carrier OS thread and runs another virtual thread there. You write simple, blocking, one-request-per-thread code and get the scalability that used to require complex reactive frameworks.

    Java 24 improvement. Earlier, a virtual thread blocking inside a synchronized block stayed “pinned” to its carrier, which could starve the system. Since Java 24 that no longer happens, so existing libraries work well on virtual threads without changes.

    Watch out. Virtual threads speed up waiting, not computing. CPU-bound work gains nothing. And don't pool them: they are cheap to create, so make a new one per task. To limit concurrent access to a resource, use a Semaphore.

    Check yourself

    Your service makes 5,000 slow HTTP calls per second. Which change helps most?

    The work is waiting, not computing. Virtual threads let each call block cheaply. A parallel stream is sized for CPU cores, and thousands of platform threads waste memory and context switches.

    Structured concurrency and scoped values

    Virtual threads make it cheap to start many tasks. These two APIs make it safe: structured concurrency treats a group of related tasks as one unit, and scoped values share data with them without the pitfalls of ThreadLocal.

    Scoped values Java 25

    A scoped value is bound for the duration of a call and is visible to everything that call does, including child threads, and then disappears. Unlike a ThreadLocal, it can't be changed by callees and can't leak.

    Structured concurrency Preview, Java 27

    Fork subtasks inside a scope; the scope can't end until they all finish. If one fails, the others are cancelled. No task outlives the code that started it, and thread dumps show the parent-child relationship.

    Preview API. Structured concurrency is in its seventh preview in Java 27, and its shape has changed between previews; the open() form above matches Java 25 to 27. Run it with --enable-preview and expect small changes before it is final.

    Every object starts with a header the JVM uses for locking, hashing and type information.     Bytecode, class loading and the JIT

    Time to look inside the .class file and follow it through the JVM. The JDK's javap tool disassembles any class.

    The JVM is a stack machine: instructions push and pop values on an operand stack. Prefixes tell you the type: i for int, l for long, a for references.

    Class loading

    Classes load lazily, the first time they are used. A class goes through loading (find the bytes), linking (verify the bytecode is safe, allocate static fields, resolve references) and initialisation (run static initialisers). Three built-in loaders handle this: bootstrap for core JDK classes, platform for other JDK modules, and application for your classpath.

    Tiered JIT compilation

    Code starts interpreted. Methods that run often are compiled quickly by the C1 compiler with profiling; the hottest are recompiled by the C2 compiler with aggressive optimisations like inlining and escape analysis, based on what the profile showed. If an assumption breaks, the JVM deoptimises and tries again.

    Reflection and annotations

    Reflection lets a program inspect and use classes it didn't know about at compile time. It is how frameworks like Spring, Hibernate and JUnit find your classes, read your annotations and call your methods.

    Writing an annotation

    An annotation is metadata attached to code. It does nothing by itself; some tool reads it, either at compile time or, with RUNTIME retention, through reflection.

    Annotation processors run inside javac and generate code at compile time instead. Lombok, MapStruct and Dagger work this way, with no runtime reflection cost.

    Final is becoming final. Reflection could always change final fields with setAccessible(true). Since Java 26 the JVM warns when code does this, as the first step toward forbidding it so the JIT can trust that final values never change. Since Java 16, deep reflection into JDK internals is blocked outright.

    Calling native code

    For decades, calling a C library from Java meant JNI: hand-written C glue, header files and crashes. The Foreign Function and Memory API, final in Java 22, does it in plain Java.

    An Arena controls the lifetime of off-heap memory: everything allocated in it is freed when it closes, and any later access fails safely instead of crashing the JVM. MemorySegment also replaces older tricks for working with large blocks of off-heap memory.

    Generate the bindings. The jextract tool reads a C header file and generates the Java bindings for you, so calling a library like SQLite or a GPU runtime is mostly a build step.

    The HTTP client

    Since Java 11 the JDK has a modern HTTP client that supports HTTP/2, WebSockets, and both blocking and asynchronous calls, without any library.

    Since Java 26 the client can also speak HTTP/3: set .version(HttpClient.Version.HTTP_3) on the builder. The JDK has no built-in JSON parser; most projects add Jackson or Gson.

    Jackson, the most widely used Java JSON library, maps JSON straight onto records and classes and back.

    Filters: code that wraps every request

    Filters are where cross-cutting concerns live: authentication, logging, character encoding, compression, CORS headers. Spring Security, for example, is a chain of filters.

    Building and deploying

    There are two ways to run servlets. The classic way packages the app as a WAR file and drops it into a running Tomcat. The modern way embeds the container inside the app, so a single executable JAR contains everything; that's what Spring Boot does.

    javax or jakarta? Older code and tutorials import javax.servlet. When Java EE moved to the Eclipse Foundation, the packages were renamed to jakarta.servlet (Jakarta EE 9, 2020). Tomcat 10 and later only accept jakarta; mixing the two is a common source of “class not found” errors.

    How frameworks build on this

    Spring MVC registers a single servlet, the DispatcherServlet, for all URLs. It reads each request, finds the @GetMapping or @PostMapping method that matches, converts JSON into your records, calls your method, and writes the result back. So the Spring Boot controller in the next lesson is a servlet application, with the plumbing written for you. Spring WebFlux is the main exception: it runs on a non-servlet, non-blocking server instead.

    Interview: explain the servlet lifecycle.

    The container loads the class and creates one instance, calls init() once, then calls service() for each request, which dispatches to doGet, doPost and so on, on many threads at once. On shutdown it calls destroy() once. Because the instance is shared, servlets must be thread-safe: no mutable per-request state in fields.

    Interview: forward vs redirect?

    A forward (request.getRequestDispatcher(path).forward(req, resp)) happens inside the server: one request, the browser's URL doesn't change, and request attributes are kept. A redirect (resp.sendRedirect(url)) tells the browser to make a new request to another URL: two round trips, a new URL in the address bar, and request attributes are lost. Redirect after a POST so refreshing doesn't resubmit the form.

    Interview: how does a session work?

    On first use, the container creates a session object on the server and sends the browser a cookie, JSESSIONID, holding its ID. Later requests carry the cookie, so the container finds the same session. Sessions live in server memory, so in a cluster you need sticky load balancing or a shared session store like Redis, which is one reason many APIs use stateless tokens instead.

    Interview: filter vs servlet?

    A servlet produces the response for a URL. A filter wraps requests on their way to servlets, and can inspect or modify the request and response, or stop the chain entirely, for example to reject an unauthenticated user. Filters run in a chain, in a configured order.

    How to answer Java interview questions

    Interviewers rarely want a definition. They want to see that you understand how something works, when you'd use it, and what can go wrong. A clear structure makes that visible, even when you're nervous.

    A four-step answer

    1. Define it in one sentence. Show you know what it is.
    2. Explain how it works. This is where most candidates stop too early.
    3. Give a tiny example. A line of code or a real situation from your work.
    4. Name a trade-off or pitfall. This is what separates a senior answer from a junior one.

    Try it on a classic: “What's the difference between ArrayList and LinkedList?”

    Model answer. Both implement List. ArrayList stores elements in a resizable array, so reading by index is O(1), and adding at the end is amortised O(1) because it grows by about 50% when full. LinkedList is a doubly linked list: inserting or removing is O(1) once you are at the node, but finding the position is O(n). In practice, ArrayList is faster for almost everything, because its elements sit next to each other in memory and CPU caches love that. I'd use LinkedList's role, a queue or deque, through ArrayDeque instead.

    Habits that cost points

    • Reciting a textbook line, like “LinkedList is faster for insertions”, without the caveat that makes it true or false.
    • Guessing confidently. “I'm not certain, but I'd reason about it like this…” scores better than a wrong fact.
    • Long silences while writing code. Think out loud, so the interviewer can follow and help.

    How to use this level. Every lesson ends with the follow-up questions interviewers usually ask next. Say your answer out loud first, then open the card to compare.

    Tell me about a Java feature you like from a recent release.

    Pick one you can explain in depth.     How HashMap works inside

    This is the single most common Java interview question, and it rewards depth. A HashMap is an array of buckets. Each key's hash code decides which bucket it goes in.

    What put(key, value) does

    1. Call key.hashCode(), then mix the high bits into the low bits: h ^ (h >>> 16). This spreads keys whose hash codes differ only in the high bits.
    2. Pick the bucket: index = hash & (capacity - 1). Capacity is always a power of two, so this is a fast replacement for %.
    3. If the bucket is empty, store a new node. If not, walk the nodes: when a key is equals to the new one, replace its value; otherwise append a node. Two different keys in one bucket is a collision.
    4. If the number of entries now exceeds capacity × load factor, resize: double the array and redistribute every entry.

    Defaults: capacity 16, load factor 0.75, so the first resize happens when the 13th entry arrives. When one bucket's chain reaches 8 nodes and the table has at least 64 buckets, that chain becomes a red-black tree, turning the worst-case lookup from O(n) into O(log n). It turns back into a list if it shrinks to 6.

    This simulator uses Java's real String.hashCode and the same bucket formula. Add keys and watch where they land. The pair Aa and BB famously have the same hash code.

    Model answer. HashMap is an array of buckets. On put, it hashes the key, spreads the bits, and masks with capacity minus one to choose a bucket. Collisions are chained in a linked list, which is converted to a red-black tree once a bucket holds 8 entries and the table is at least 64 long. get repeats the hashing and then uses equals to find the exact key, which is why equals and hashCode must agree. When size passes capacity times the load factor of 0.75, it doubles and rehashes. Average lookup is O(1). It allows one null key, which goes in bucket 0, and it isn't thread-safe.

    A favourite follow-up: build an LRU cache

    What happens when two keys have the same hashCode?

    They land in the same bucket and are chained. get walks the chain and uses equals to find the right one. Lookups still work, they're just slower. With many collisions in one bucket, Java 8+ converts the chain to a tree.

    Why must capacity be a power of two?

    So the bucket index can be computed with a bitwise AND, hash & (n - 1), which is much faster than %. It also makes resizing cheap: each entry either stays at its index or moves to index + oldCapacity, decided by a single bit.

    What if you change a key's fields after putting it in the map?

    If the change affects hashCode, the entry is now in the wrong bucket. get looks in the new bucket and returns null, even though the entry is still in the map, leaking memory. That's why keys should be immutable, like String, Integer or records with immutable fields.

    Why convert to a tree at 8, and not always use trees?

    Tree nodes take about twice the memory of list nodes. With a decent hash function, a chain of 8 is statistically extremely rare, so trees almost never appear. They exist as a defence against bad hash codes or deliberate attacks that put many keys into one bucket. Trees work best when keys are Comparable.

    How is HashSet implemented?

    A HashSet wraps a HashMap. Each element is stored as a key, with one shared dummy object as the value. add returns whether put returned null.

    HashMap vs LinkedHashMap vs TreeMap?

    HashMap: no order, O(1). LinkedHashMap: also keeps a doubly linked list through the entries, so it iterates in insertion or access order. TreeMap: a red-black tree sorted by key, O(log n), with navigation methods like floorKey and subMap.

    ConcurrentHashMap and safe iteration

    Most collections, like ArrayList and HashMap, keep a modification counter. Their iterators are fail-fast: if the collection changes during iteration, other than through the iterator itself, the next step throws ConcurrentModificationException. It happens even in a single thread:

    What happens here?

    ConcurrentHashMap rejects null keys and values. In a concurrent map, get(k) returning null must mean “absent”; if nulls were allowed, you couldn't tell “absent” from “mapped to null” without a second call, and another thread could change the answer in between.

    When would you use CopyOnWriteArrayList?

    When reads vastly outnumber writes, like a list of event listeners. Every write copies the whole array, so it's terrible for frequently changing data, but reads and iteration need no locking.

    Is ConcurrentHashMap's size() exact?

    It's exact when nothing is changing, but during concurrent updates it's an estimate, because counting while other threads add and remove can't be both exact and lock-free. Use mappingCount() for large maps, since it returns a long.

    How would you implement a producer-consumer queue?

    Use a BlockingQueue, like ArrayBlockingQueue or LinkedBlockingQueue. put blocks when it's full and take blocks when it's empty, so producers and consumers coordinate without any explicit locking. The thread coordination lesson shows the hand-written version interviewers sometimes ask for.

    Comparable vs Comparator

    Deeper point. Never write return a - b; in a comparison: subtracting large values overflows and gives the wrong sign. Use Integer.compare.     Initialization order

    Static initialisation happens once, when the class is first used, parent before child. Then, for every new, each class from the top down runs its field initialisers and instance blocks in source order, followed by its constructor body.

    Can a constructor be overridden?

    No. Constructors aren't inherited, so there's nothing to override. They can be overloaded, and a subclass constructor always calls a parent constructor, explicitly or implicitly.

    Why is calling an overridable method from a constructor dangerous?

    The parent constructor runs before the child's fields are initialised. If it calls a method the child overrides, that method runs on a half-built object and sees null or zero fields. Make such methods private or final. Java 25's flexible constructor bodies help, by letting the child assign its fields before calling super.

    Can main be overloaded?

    Yes, like any method, but the launcher only calls the entry-point signature. Since Java 25 the launcher also accepts an instance main() without parameters, and prefers main(String[]) if both exist.

    What happens if a static block throws an exception?

    The first use of the class throws ExceptionInInitializerError. The class is then marked as failed, and every later attempt to use it throws NoClassDefFoundError, which can be confusing in logs if you only see the later error.

    Immutable classes and singletons

    “Write an immutable class” and “write a thread-safe singleton” are both coding questions with a checklist behind them. Interviewers watch whether you remember every item.

    Writing an immutable class

    If a field holds a mutable object, like a Date or an ArrayList, you must copy it both when it comes in and when it goes out. Otherwise callers can change your “immutable” object through the reference they still hold. A record gives you steps 2 and 4 for free.

    Four singletons, from worst to best

    Why does double-checked locking need volatile?

    Creating an object is several steps: allocate, run the constructor, assign the reference. Without volatile, the CPU or JIT may reorder them, so another thread can see a non-null instance before its constructor has finished, and use a half-built object. volatile forbids that reordering.

    How can a singleton be broken?

    Reflection can call the private constructor with setAccessible(true). Deserialization creates a new instance unless you add readResolve. clone can copy it if it's Cloneable. Two class loaders each get their own copy. The enum version is immune to the first three.

    Is singleton a good pattern?

    Use it carefully. It's global state, which hides dependencies and makes testing hard, since you can't easily swap in a fake. In modern applications, a dependency injection framework like Spring creates one instance and passes it to whoever needs it, giving you the “one instance” benefit without the drawbacks.

    Why are immutable objects good for concurrency?

    They can't change, so they can be shared between threads with no locks, and once properly constructed with final fields, every thread is guaranteed to see the same values. No race conditions are possible on data that never changes.

    sleep() vs wait()?

    sleep is a static method on Thread; it pauses the current thread and keeps any locks it holds. wait is a method on Object; it must be called while holding that object's lock, and it releases the lock while waiting until notified.

    Why are wait and notify on Object, not Thread?

    Because threads wait on a condition tied to some shared object, and every object can serve as a lock (a monitor). The waiting is about the lock, not about a particular thread.

    Runnable vs Callable?

    Runnable.run() returns nothing and can't throw checked exceptions. Callable.call() returns a value and can throw. Submitting a Callable to an executor gives you a Future to get the result.

    How do you stop a thread?

    Cooperatively: call thread.interrupt(), and have the thread check Thread.currentThread().isInterrupted() or handle InterruptedException by finishing up. Thread.stop() was unsafe because it could leave objects half-updated; since Java 20 it just throws UnsupportedOperationException.

    What is a daemon thread?

    A background thread that doesn't keep the JVM alive. When only daemon threads remain, the JVM exits. GC threads are daemons. Set it with setDaemon(true) before start(). Virtual threads are always daemon threads.

    What's the risk of ThreadLocal in a thread pool?

    Pool threads live forever, so a value set and never removed stays attached to that thread: a memory leak, and worse, the next task on that thread may see the previous user's data. Always remove() in finally. Java 25's ScopedValue avoids the problem by design.

    More multithreading questions

    Concurrency is where interviewers separate experienced Java developers from the rest. These questions go beyond the basics in the previous lesson. Every “what happens” answer here was checked by running the code on JDK 25.

    Visibility and the memory model

    What is the Java Memory Model, and what does “happens-before” mean?

    The Java Memory Model defines when a write by one thread is guaranteed to be visible to another. Without that guarantee, CPU caches and compiler reordering mean a thread may see stale values, or see writes in a different order. “A happens-before B” means everything A did is visible to B. The main rules: unlocking a monitor happens-before the next lock of it; a volatile write happens-before every later read of that variable; thread.start() happens-before anything the new thread does; and everything a thread does happens-before another thread returns from join() on it.

    What does volatile guarantee, and what doesn't it?

    It guarantees visibility, every read sees the latest write, and ordering, since accesses can't be reordered around it. It does not make compound actions atomic. Use it for a flag one thread writes and others read, like a stop signal. For counters, use AtomicInteger or a lock.

    Check yourself

    Two threads each run count++ one million times on a volatile int. What's printed after both finish?

    count++ is a read, an add and a write. Two threads can read the same value and both write back the same result, losing an update. In our test runs we got 1,620,196 and 1,594,399, but also 2,000,000 when the threads happened not to collide. That's what makes race conditions dangerous: they pass tests by luck. Fix it with AtomicInteger.incrementAndGet().

    Are reads and writes of long and double atomic?

    Not guaranteed. The Java Language Specification allows a non-volatile 64-bit long or double write to happen as two 32-bit halves, so another thread could see half of an old value and half of a new one. Declaring the field volatile makes reads and writes of it atomic. In practice 64-bit JVMs don't split them, but the guarantee only comes with volatile.

    What is safe publication, and why do final fields matter?

    Publishing an object means making it reachable by other threads. If you assign it to a plain field without synchronisation, another thread might see the reference before the constructor's writes are visible, a half-built object. Safe ways to publish: a final field, a volatile field, a static initialiser, or a concurrent collection. The JMM guarantees that an object's final fields are fully visible to any thread that sees the object, as long as this didn't escape during construction. That's a key reason immutable objects are thread-safe.

    Locks

    Which lock does a synchronized method use?

    An instance method locks on this; a static method locks on the Class object, such as Account.class. A synchronized (obj) block locks whatever object you name, which lets you lock less code and use a private lock object that outside code can't interfere with. Locks are reentrant: a thread that holds a lock can enter other blocks synchronized on the same lock without deadlocking itself.

    Check yourself

    One thread is inside staticWork() when another calls acc.instanceWork(). Does the second thread wait?

    The static method holds the lock on Account.class; the instance method needs the lock on acc. Different objects, so no waiting. Running it prints “static in”, “instance in”, then both “out” lines. A classic bug: protecting a static field with an instance-level lock doesn't protect it at all.

    synchronized vs ReentrantLock?

    Both are reentrant mutual-exclusion locks with the same memory guarantees. synchronized is simpler and releases automatically, even on exceptions. ReentrantLock adds features: tryLock() with or without a timeout, lockInterruptibly(), an optional fairness policy, and several Condition objects per lock, for example “not full” and “not empty” in a queue. The cost is that you must call unlock() in a finally block. Since Java 24, virtual threads no longer get pinned inside synchronized, so the old advice to replace it with ReentrantLock for virtual threads no longer applies.

    When would you use ReadWriteLock or StampedLock?

    When data is read far more often than written. ReentrantReadWriteLock lets many readers in at once, but a writer gets exclusive access. StampedLock adds optimistic reads: read without locking, then call validate(stamp) to check that no write happened meanwhile, and retry with a real lock if one did. It's faster but harder to use correctly, and it isn't reentrant.

    Deadlock, livelock and starvation

    How do you detect and prevent a deadlock?

    A deadlock needs four conditions at once: mutual exclusion, holding a lock while waiting for another, no forced release, and a circular wait. Break any one and it can't happen. In practice: always acquire locks in a consistent global order, for example by account ID; use tryLock with a timeout and back off; hold locks for as short a time as possible; and never call unknown code while holding a lock. To detect one, take a thread dump; the JVM finds deadlocks itself:

    What are livelock and starvation?

    In a livelock, threads aren't blocked but keep reacting to each other without progress, like two people stepping aside in a corridor in the same direction forever, for example two threads that both release and retry a lock in lockstep. Random back-off fixes it. In starvation, a thread never gets the resource because others always win, for example with an unfair lock under heavy contention or long-running tasks hogging a small pool. Fair locks and bounded work per task help.

    Race condition vs data race?

    A data race is a memory-model term: two threads access the same variable, at least one writes, and nothing orders them. A race condition is a logic bug where the result depends on timing. They often overlap, but not always: a check-then-act sequence on a ConcurrentHashMap, like if (!map.containsKey(k)) map.put(k, v), has no data race, because each call is thread-safe, yet it's still a race condition. That's why putIfAbsent exists.

    Coordination tools and atomics

    CountDownLatch vs CyclicBarrier vs Semaphore vs Phaser?

    CountDownLatch: one or more threads wait until a count reaches zero, like waiting for 3 services to start; single-use. CyclicBarrier: a fixed group of threads wait for each other at a meeting point, then all continue; reusable for repeated rounds. Semaphore: limits how many threads use a resource at once, like 10 database connections. Phaser: a flexible, reusable barrier where parties can register and leave between phases.

    How does AtomicInteger work without locks? What's the ABA problem?

    It uses compare-and-swap (CAS), a single CPU instruction: “set this to the new value only if it still holds the value I read”. If another thread changed it in between, CAS fails and the operation retries. The ABA problem: a value changes from A to B and back to A, so CAS succeeds even though the state changed underneath, which matters in lock-free data structures. AtomicStampedReference fixes it by pairing the value with a version number. Under very heavy contention, LongAdder beats AtomicLong by spreading updates across several cells.

    thenApply vs thenCompose vs thenCombine in CompletableFuture?

    thenApply transforms the result with a normal function, like map. thenCompose chains a function that itself returns a CompletableFuture, flattening it, like flatMap; use it for dependent async calls. thenCombine waits for two independent futures and merges their results. Also know that async stages run on the common ForkJoinPool by default; pass your own executor for blocking work so it doesn't starve parallel streams and other users of the shared pool.

    What is the Fork/Join framework?

    A pool designed for divide-and-conquer tasks: a RecursiveTask splits itself into subtasks, forks them, and joins their results. Each worker has its own deque of tasks, and idle workers steal tasks from the back of busy workers' deques, keeping all cores busy. Parallel streams and CompletableFuture's async methods use its shared common pool.

    Serialization and cloning

    Both are older features that modern code avoids, but interviewers still ask about them, because they test your understanding of object references and object identity.

    Serialization

    If you don't declare serialVersionUID, Java computes one from the class's structure, so adding a field makes old serialized data unreadable with InvalidClassException. Records serialize safely through their canonical constructor.

    Shallow vs deep copy

    A shallow copy copies each field's value, so both objects share the same members list; changing one changes the other. A deep copy also copies the objects those fields refer to.

    The modern answer. Cloneable is widely considered broken: it's a marker interface that changes how a protected method in Object behaves, and clone skips constructors. Prefer a copy constructor (new Team(other)) or a static factory. For serialization, prefer JSON or Protocol Buffers; Java's built-in serialization has been the source of many security vulnerabilities.

    What is a marker interface? Give examples.

    An interface with no methods that tags a class with a property: Serializable, Cloneable, RandomAccess. Today an annotation usually does the same job, but a marker interface has one advantage: it's a type, so the compiler can check it.

    What if a parent class isn't Serializable?

    The child can still be serializable, but the parent's fields aren't saved. On deserialization, the parent's no-argument constructor runs to initialise them, and it must exist and be accessible, or you get an exception.

    transient vs volatile?

    Unrelated, despite sounding similar. transient is about serialization: skip this field. volatile is about concurrency: every read and write goes to main memory and is visible to all threads.

    Serializable vs Externalizable?

    With Serializable, Java writes fields automatically. With Externalizable, you write writeExternal and readExternal yourself, which gives full control and can be faster, and the class needs a public no-argument constructor.

    Diagnosing a slow application

    1. Measure first. Which requests are slow, since when, and what changed: a deploy, traffic, data volume?
    2. Check the resources. CPU, memory, GC time, thread count, database and downstream latency.
    3. Take thread dumps. Two or three, five seconds apart, with jcmd <pid> Thread.print. Threads stuck in the same place point to a lock, a slow query or a slow external call.
    4. Check GC. Enable -Xlog:gc*. Long or frequent pauses with an old generation that stays full after collections mean a leak or an undersized heap.
    5. Profile. A JDK Flight Recorder recording shows hot methods, allocations and lock contention with low overhead, safe in production.
    6. For leaks, take a heap dump and open it in Eclipse MAT. Look for the largest retained objects and what keeps them alive.
    Can Java have memory leaks if it has a garbage collector?

    Yes. The GC frees only objects that are unreachable. If your code keeps a reference you no longer need, like an ever-growing static map, unremoved listeners, a ThreadLocal in a pool, or an unclosed resource, the object stays reachable and is never freed.

    What are GC roots?

    The starting points the GC uses to find live objects: local variables and parameters on every thread's stack, static fields of loaded classes, active threads, and references held by native code. Anything not reachable from a root is garbage.

    Strong, soft, weak and phantom references?

    Strong: normal references; never collected while reachable. Soft: collected only when memory is low, useful for caches. Weak: collected at the next GC once only weakly reachable; WeakHashMap uses weak keys. Phantom: never returns the object; used with a reference queue to run clean-up after an object is collected, as Cleaner does.

    Heap is 90% full. Should you just increase -Xmx?

    Not first. If usage keeps climbing after every full GC, it's a leak, and a bigger heap only delays the crash. If usage is high but stable, the heap may genuinely be too small. Look at the GC logs to tell which, then decide.

    Rapid-fire round

    Short questions that often open an interview or fill the last five minutes. Each answer should take you under thirty seconds. Say yours out loud, then check.

    Is Java pass-by-value or pass-by-reference?

    Always pass-by-value. For objects, the value passed is a copy of the reference, so a method can change the object but not make the caller's variable point somewhere else.

    JDK vs JRE vs JVM?

    The JVM runs bytecode. The JRE is the JVM plus the standard libraries. The JDK is the JRE plus development tools like javac. Since Java 11 there's no separate JRE download.

    Why is Java “platform independent”?

    Source compiles to bytecode, not machine code, and every platform has its own JVM that runs the same bytecode. The JVM itself is platform-specific.

    == vs equals()?

    == compares primitive values, or for objects, whether two references point to the same object. equals compares logical content, as defined by the class.

    How many objects does new String("hi") create?

    Up to two: the literal "hi" in the string pool, if it isn't already there, and a new String object on the heap.

    Why store passwords in char[] instead of String?

    A String is immutable and may stay in memory until garbage collected, and can end up in logs or heap dumps. A char[] can be overwritten with zeros as soon as you're done. Console.readPassword returns char[] for this reason.

    Can an abstract class have a constructor? Can an interface?

    An abstract class can, and it runs when a subclass is instantiated. An interface can't; it has no instance state to initialise.

    How does Java handle the diamond problem?

    Classes have single inheritance, so it can't occur with state. With interfaces' default methods, if two provide the same method, the class must override it and can pick one with InterfaceName.super.method().

    Why were default methods added?

    To evolve interfaces without breaking implementers. Java 8 added stream() to Collection; as a default method, every existing collection class got it without changes.

    What is a functional interface?

    An interface with exactly one abstract method, like Runnable, Comparator or Function. It can be implemented with a lambda. @FunctionalInterface makes the compiler enforce it.

    Checked vs unchecked exceptions?

    Checked exceptions extend Exception but not RuntimeException; the compiler forces callers to catch or declare them. Unchecked ones extend RuntimeException or Error; they usually signal bugs.

    Error vs Exception?

    An Error is a serious JVM-level problem, like OutOfMemoryError, that an application shouldn't try to catch. An Exception is a condition a program can reasonably handle.

    ArrayList vs Vector?

    Both are resizable arrays. Vector synchronizes every method and is legacy. Use ArrayList, and a concurrent collection if threads share it.

    start() vs run()?

    start() creates a new thread that then calls run(). Calling run() directly just executes it on the current thread, like any method.

    volatile vs synchronized vs atomic?

    volatile gives visibility but not atomicity, so count++ is still unsafe. synchronized gives both, with a lock. Atomic classes like AtomicInteger give both for single variables without locking.

    Platform threads vs virtual threads?

    Platform threads map one-to-one to OS threads and are expensive. Virtual threads are scheduled by the JVM onto a few carrier threads, cost a few hundred bytes, and can number in millions. Use them for blocking I/O work, not CPU-heavy work.

    Record vs a regular class with Lombok?

    A record is a language feature: immutable, with generated constructor, accessors, equals, hashCode and toString, and it works with record patterns. Lombok is a compile-time library and can generate mutable classes too. For plain data carriers, prefer records.

    What does the static keyword mean on a class, method, field and block?

    It means “belongs to the class, not an instance”. A static field is shared; a static method needs no object; a static block runs once when the class initialises; a static nested class has no link to an outer instance. Top-level classes can't be static.

    What is the string pool?

    A JVM-wide table of unique string literals, stored on the heap since Java 7. Identical literals share one object. intern() adds a runtime string to the pool or returns the pooled copy.

    What is autoboxing, and its pitfall?

    Automatic conversion between primitives and wrappers, like int to Integer. Pitfalls: comparing wrappers with ==, unboxing a null throws NullPointerException, and boxing in hot loops creates garbage.

    What does the JIT compiler do?

    It watches which code runs often at runtime and compiles those methods to optimised native machine code, using profile information like which branches are taken and which types actually appear.

    Which GC does Java use by default?

    G1 on most server-class machines. ZGC is the main low-pause alternative, enabled with -XX:+UseZGC.
